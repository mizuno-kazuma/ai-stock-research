# 仕様書の追加・改訂

この仕様書群は「読んで実装できること」を基準にしている。抽象的な方針だけの文書は価値がない。
以下の型に従う。

関連: [README.md](../../../README.md)、[docs/](../../../docs/)

## 1. どこに書くか

新しい内容を追加する前に、既存の16文書のどれかに収まらないかを確認する。文書を増やすより、
既存文書に節を追加する方がよい。

| 内容 | 追記先 |
| --- | --- |
| 新しいデータソース | `02-data-ingestion.md` |
| 新しいテーブル・列 | `03-data-model.md` |
| 新しい特徴量・モデル・検証手法 | `04-analysis-engine.md` |
| スコアリング・推奨ロジックの変更 | `05-scoring-screening.md` |
| 開示資料のURL生成・要約キャッシュ | `06-filings-access.md` |
| LLMのルーティング・プロンプト・RAG | `07-llm-rag.md` |
| ジョブの追加・順序変更・ガードレール | `08-agent-loop.md` |
| エンドポイントの追加・変更 | `09-api-spec.md` |
| PWA・配信・クラウド移行 | `10-mobile-pwa.md` |
| シークレット・バックアップ・監視・コスト | `11-security-ops.md` |
| テストの追加 | `12-testing-validation.md` |
| Phase の定義・完了条件 | `13-roadmap.md` |
| 自動発注の設計 | `14-future-brokerage.md` |
| Windows/WSL2 固有の問題 | `15-windows-runtime.md` |
| 画面の追加・変更 | `docs/ui/screens/` |
| トークン・コンポーネント・状態 | `docs/ui/` の該当ファイル |

新規文書を作る基準は「既存のどの文書の主題にも属さず、かつ2000字以上になる」場合のみ。

## 2. 文書の構成

### 見出しの規則

- H1 は1文書に1つ。文書のタイトル
- H2 は番号付き（`## 1. 目的`）。参照時に節番号で指せるようにする
- H3 は `### 1.1` 形式
- H4 以下は使わない。必要になったら節を分ける

### 冒頭

タイトル直後に、その文書が何を決めているかを2-4文で書く。目次は書かない（GitHub が自動生成する）。

```markdown
# 04. 分析エンジン

特徴量の定義、予測モデル、検証手法を定める。この章の基本姿勢は「予測は当たらない前提で作る」
ことで、すべての予測に信頼区間とベースライン比較を伴わせる。ここで定めた検証手法から外れた
方法で得た成績は、この製品では採用しない。
```

### 末尾

「関連文書」節を置き、依存関係のある文書へのリンクを列挙する。

## 3. 具体性の基準

以下を満たさない記述は書き直す。

| 対象 | 満たすべき水準 | 悪い例 | 良い例 |
| --- | --- | --- | --- |
| テーブル | 列名・型・主キー・NULL可否がある | 「価格を保存する」 | `prices_daily(ticker VARCHAR, date DATE, close DOUBLE, ...)` PK `(ticker, date)` |
| エンドポイント | メソッド・パス・クエリ・レスポンス例がある | 「推奨を取得するAPI」 | `GET /api/v1/recommendations?market=JP&horizon=H20` + JSON例 |
| 設定 | キー名・型・既定値・単位がある | 「コスト上限を設定できる」 | `llm.daily_cap_usd: float = 1.5`（USD/日） |
| 計算式 | 数式または擬似コードがある | 「モメンタムを計算する」 | `(close_t / close_{t-252d}) - (close_t / close_{t-21d})` |
| 閾値 | 数値と単位がある | 「ボラが高い銘柄を除外」 | 「実現ボラティリティ（60営業日・年率）が40%を超える銘柄を除外」 |
| 判断基準 | 却下条件として書く | 「慎重に判断する」 | 「DSR の p値が0.05以上なら採用しない」 |

### 禁止する書き方

- 「適切に」「必要に応じて」「柔軟に」「best practice に従い」— 何をするかが決まっていない
- 「将来的に検討する」だけで終わる記述 — 検討する条件を書く
- 効果の根拠がない断定 — 「精度が向上する」ではなく「Rank IC が 0.02 から 0.03 に改善した（n=248）」

### 落とし穴は「原因 + 対策」で書く

Windows/WSL2 の章がこの形式を取っている。他の章でも踏襲する。

```markdown
### 3.2 日本語が cp932 で読まれる

**原因**: 日本語ロケールの Windows では Python のデフォルトエンコーディングが cp932 になる。
EDINET の資料を読むと `UnicodeDecodeError` が発生する。UTF-8 モードがデフォルトになるのは
Python 3.15 以降。

**対策**: `PYTHONUTF8=1` を設定し、加えて `open()` に `encoding="utf-8"` を常に明示する。
Ruff の `PLW1514` を CI で有効にして機械的に検出する。
```

対策だけを書くと、なぜそれが必要かが伝わらず、後から「不要では」と削除される。

## 4. 確認が必要な事実の扱い

外部の事実（APIのエンドポイント、価格、レート制限、プラン内容）は変わる。断定せず、確認を促す。

```markdown
J-Quants API v2 は `x-api-key` ヘッダで認証する。無料プランのレート制限は毎分5リクエスト、
データは12週間遅延する（本書執筆時点）。**エンドポイントのパス、認証方式、プラン内容は変更
される可能性があるため、実装前に公式ドキュメントで確認すること。**
```

以下の種類の情報には必ず確認注記を付ける。

- API のエンドポイントパス
- 認証方式とヘッダ名
- レート制限の具体値
- 料金・プラン内容
- LLM のモデル名と単価
- 外部サービスの利用規約上の制約

LLM のモデル名と単価は特に変動が速い。文書には「`models.yaml` に集約し、コードにハードコードし
ない」ことを書き、具体値は参考値として `last_verified` の日付付きで示す。

## 5. 相互参照

- リンクは相対パス。節番号まで指す
  `[04-analysis-engine.md](04-analysis-engine.md) §4.1`
- 同じ内容を2箇所に書かない。片方を正とし、もう片方はリンクにする
- 矛盾しうる箇所には、どちらが優先かを明記する
  「画面仕様とAPI仕様が食い違う場合、フィールド名はAPI仕様、表示はUI仕様が優先」

同じ数値（コスト上限、レート制限、閾値）が複数の文書に出てくる場合、正となる文書を決め、他は
参照にする。数値の二重管理は必ず食い違う。

## 6. Figma Make 用UI文書の言語規則

`docs/ui/` は他の文書と規則が違う。

| 要素 | 言語 |
| --- | --- |
| 構造説明・指示文 | 英語（生成品質のため） |
| 画面内の実テキスト | 日本語 |
| 表記形式 | `label_en` / `label_ja` の対で記載 |
| フィールド名・ルート・コード | 英語 |
| 開示資料のタイトル・引用 | 原文のまま |

画面仕様ファイルは**全10画面で節構成を完全に一致させる**。Figma Make が一様に解析できることが
目的なので、1ファイルだけ節を増やしたり順序を変えたりしない。

```
# NN. Screen Name
## Purpose
## Route
## Layout  (### Desktop / ### Tablet / ### Mobile)
## Component tree
## Content spec
## States
## Interactions
## Data source
```

Content spec には実データ例をインラインで書く。lorem ipsum は使わない。`sample-data.json` に
対応するデータがあることを確認する。

## 7. 改訂時のチェック

既存文書を変更したら、以下の整合性を確認する。変更が波及する範囲が広い。

| 変更したもの | 併せて確認する場所 |
| --- | --- |
| テーブル・列 | `03-data-model.md`、マイグレーション、`09-api-spec.md` のレスポンス、`docs/ui/` の表示項目 |
| エンドポイント | `09-api-spec.md`、`packages/schemas`、`docs/ui/screens/*.md` の Data source 節 |
| 設定キー | `11-security-ops.md`、`.env.example`、`ui/screens/10-settings.md` |
| 特徴量 | `04-analysis-engine.md`、`factors.yaml`、`ui/screens/04-screener.md` のフィルタ項目 |
| reason code | `05-scoring-screening.md`、`ui/components.md` の一覧、`sample-data.json` |
| ジョブ | `08-agent-loop.md`、`ui/screens/08-agent-console.md`、`ui/screens/10-settings.md` のスケジュール表 |
| テストID | `12-testing-validation.md`、`ui/screens/07-model-lab.md` のリーク検査一覧 |
| Phase の完了条件 | `13-roadmap.md` |
| 数値の閾値 | 同じ数値が出てくる全文書（`rg` で検索する） |

数値を変えたときは必ず全文検索する。

```bash
rg -n '1\.5|1,650|12週|0\.03' docs/ | head -40
```

## 8. コミットの粒度

1コミット = 1つの論理的な変更。文書横断の整合性修正は、内容の変更とは分けてコミットする。

```
docs: J-Quants の v2 エンドポイントを実装時の実測値に更新
docs: 上記に伴う相互参照の整合性を修正
```

## 完了条件

- [ ] 節が番号付きで、参照可能
- [ ] 具体性の基準を満たす（列名・型・数式・閾値・エンドポイントが具体）
- [ ] 落とし穴を「原因 + 対策」で書いた
- [ ] 変わりうる事実に確認注記を付けた
- [ ] 同じ内容を2箇所に書いていない
- [ ] 相互参照の整合性を確認した（上の表）
- [ ] UI文書の場合、10画面の節構成が一致している
- [ ] `README.md` の索引を更新した（新規文書の場合）
- [ ] 絵文字を使っていない
